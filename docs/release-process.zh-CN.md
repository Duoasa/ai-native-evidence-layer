# 发布流程

简体中文 | [English](release-process.md)

当前没有任何发布版本。本流程规定维护者在发布前必须具备的最低证据。

## 版本化对象

- **仓库版本：** 经过审核的 Schema、工具、文档、示例与生成制品快照。在专门的协议版本策略通过前，仓库版本遵循语义化版本，并保持在 `1.0` 之前。
- **Schema 版本：** 每个兼容对象都必须声明。已经发布的 Schema 文件不可修改；破坏性契约变更必须使用新的 Schema 版本并提供迁移说明。
- **目录快照：** 由节点 ID、快照日期、制品哈希及其实现的 Schema 版本共同标识。新目录快照不自动产生新的协议版本。

## 发布前提

- 范围与兼容性影响已记录；必要时已有通过的规格或 ADR。
- 目录材料已经完成许可、来源与隐私审核。
- `CHANGELOG.md`、示例、迁移说明和双语规范文档准确描述本次发布。
- 在干净检出中执行 `npm ci` 与 `npm run check` 均通过。
- 生成文件能够完全重现，且 `dist/manifest.json` 与发布文件一致。
- CI 遵循最小权限，不嵌入密钥；已知重大安全问题已经解决或明确披露。
- 维护者已记录批准；自动化本身不能授权对外发布。

## 发布步骤

1. 冻结候选提交，并在干净检出中执行完整门禁；
2. 审核差异、来源、许可、隐私、安全和兼容性；
3. 设置目标版本，并将相应条目移出 **未发布**；
4. 创建带签名的附注 Git Tag，不得重写现有发布标签；
5. 从该标签创建 GitHub Release，并在适用时附加确定性制品与 Manifest；
6. 从公开入口下载制品，核对哈希与内容，并将结果记录到 `docs/handoff.md`。

远程发布、标签和 Release 必须在实际发布时获得维护者明确授权。

## 纠正与撤回

- 不得静默替换已发布制品或移动其标签；
- 发布新的纠正版本，并说明受影响版本与迁移路径；
- 若制品暴露敏感数据或造成紧急安全风险，可在必要时限制访问，同时以最小披露方式保留可审计事件记录并发布安全替代物；
- 数据纠正应保留有支持证据的历史声明并发布新目录快照，不得重写已发布历史。
